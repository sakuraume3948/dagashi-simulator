# 駄菓子シミュレータ

駄菓子屋での買い物を再現する Web アプリケーション。予算を決めてお任せで買い物をする「予算モード」と、10連ガチャのように駄菓子を引く「ガチャモード」の 2 つがある。

商品データは実在の駄菓子 156 件。価格は駄菓子問屋の希望小売価格を取得したもので、想像で決めた値は含まない。

## 機能

### 予算モード

指定した金額の範囲内で、駄菓子屋のカゴに入れていくようにランダムで商品を選ぶ。

| 設定項目 | 内容 |
| --- | --- |
| 予算 | 数値入力またはプリセット（100 / 300 / 500 / 1000 円） |
| 商品の個数上限 | 味単位の上限。「うまい棒 めんたい味は 3 本まで」 |
| シリーズの個数上限 | 味をまたいだ上限。「うまい棒は全部で 3 本まで」 |
| カテゴリ | 7 カテゴリから対象を選択 |

- 合計金額が予算を超えることはない。おつりは出る
- 2 つの個数上限は同時に適用され、厳しい方が効く
- 2 つの上限は双方向に連動する。商品上限を上げるとシリーズ上限が追従して上がり、シリーズ上限を下げると商品上限が追従して下がる（`0` = 無制限は常に成立するため連動しない）
- 味違いを持たない商品は「自分ひとりだけのシリーズ」として数える。そうしないと、商品上限を無制限にしたときに単独商品だけが無制限に買える状態になる

### ガチャモード

1 連または 10 連で駄菓子を引く。高価な商品ほど出にくい。天井や確定枠はない。

## データの作り方

商品データは 3 つの情報源から集め、手動の上書きを重ねて `lib/data.ts` を生成している。

```
data/sources/inokuchi.json   商品名・希望小売価格・シリーズ・商品ページURL
data/sources/yahoo.json      メーカー名とJANコードの「候補」（照合材料。単独では採用しない）
data/sources/rakuten.json    メーカー名・JANコード（両APIを突き合わせた採用結果）
data/overrides.json          手動の上書き（★スクリプトは絶対に書き換えない）
        │
        │  npm run build:data
        ↓
lib/data.ts                  生成物
```

### 取得と生成を分けている

`fetch:*` は `data/sources/*.json` を書くだけで、`lib/data.ts` には触らない。生成は `build:data` が担当する。

- 解析ロジックを直すたびにサイトへ再アクセスしなくて済む
- 複数の情報源を対等に扱える
- 「取得が悪いのか生成が悪いのか」を切り分けられる

取得したページやAPIレスポンスは `data/.cache/` に保存され、2 回目以降は問い合わせない。`-- --refresh` を付けたときだけ取り直す。

### 手動の上書きは消えない

`data/overrides.json` に書いた値は、何度データを取り直しても失われない。スクリプトはこのファイルを書き換えないため。

```json
{
  "items": {
    "inokuchi-18409": { "maker": "菓道", "_reason": "..." },
    "inokuchi-48621": { "exclude": true, "_reason": "..." }
  }
}
```

`_` で始まるキーは人間向けの注釈で、商品データには取り込まれない。判定根拠はすべて `_reason` に記録してある。

### 価格の表記は 4 通りある

井ノ口は商品名の中に希望小売価格を書いている。ただし表記が揃っていない（179 商品の実測）。

| 表記 | 件数 | 例 |
| --- | --- | --- |
| 先頭に `#` / `＃` + 数字 | 153 | `＃15 うまい棒 チーズ味` |
| 先頭に `♯` + 数字 | 5 | `♯20 キャラメルの魔法（28入）` |
| 先頭が記号なしの数字 | 6 | `40すっぱいぶどうにご用心（20入）` |
| 末尾に `#NN` | 2 | `3本きなこ飴棒(15袋入り）#35` |
| 価格表記なし | 12 | `チロルチョコバラエティパック（25粒入り）` |

**`♯` は U+266F（音楽の嬰記号）**で、`#`（U+0023）とも `＃`（U+FF03）とも別の文字。見た目がほぼ同じなので、文字クラスに入れ忘れると 5 件が静かに落ちる。

**末尾の `#NN` を先に見る。** `3本きなこ飴棒(15袋入り）#35` の先頭「3」は本数で、価格は末尾の 35。先頭から読むと 3 円になる。

価格表記が無い 12 件は取り込めない。価格欄に「148ｇ入1袋」のような単位しか書かれていないため。多くは大袋・箱売りで、単品の駄菓子ではない。

### 価格が確定しない商品は出力しない

価格がなければ予算モードもガチャも成立しないため、価格未確定の商品は `lib/data.ts` に含めず、警告として一覧表示する。`exclude: true` を指定した商品も同様。

必須なのは商品名と価格だけで、メーカー名・販売単位は取得できない情報源があるため `null` を許容している。

### 公開アプリは外部APIを呼ばない

取得は開発者の手元でのみ行い、結果をリポジトリに保存する。デプロイされたアプリは生成済みの `lib/data.ts` を読むだけなので、訪問者が何人来ても外部サイトへのアクセスは発生しない。

画像と商品説明文は取得していない（著作物のため）。商品名・価格・メーカー名・JANコードという事実情報のみを保持している。

### APIキー

`fetch:yahoo` と `fetch:rakuten` を動かす場合のみ、`.env.local` に以下が必要。`.gitignore` の `.env*` で除外される。

```
YAHOO_CLIENT_ID=...
RAKUTEN_APPLICATION_ID=...
RAKUTEN_ACCESS_KEY=...
```

楽天は 2026 年 2 月のインフラ刷新以降、`Referer` / `Origin` ヘッダーが必須。アプリ登録時の「許可されたWebサイト」と一致していないと 503 になる（`scripts/fetch-rakuten.mts` の `ALLOWED_SITE` で指定）。

### メーカー名の調べ方

商品名で検索して 1 件だけ拾うと誤マッチが混ざる。実測では Yahoo! と楽天の両方がメーカー名を返した 20 件のうち 12 件が食い違い、しかもどちらが正しいかは商品によって違った。そのため次の順で判定している。

1. **Yahoo! と楽天が一致したもの**を採用（片方だけでは採用しない）
2. **JAN の事業者コードでグループ化して多数決** — JAN の先頭 7 桁は事業者ごとの固有コード。単品では誤マッチに埋もれる答えが、グループ化すると浮かび上がる
3. **JAN を鍵に楽天プロダクトへ完全一致照会** — 返ってきた商品名と照合し、食い違えば JAN 側が誤りと判断して捨てる
4. **Web 検索で裏取り**

推測では埋めない。この 4 段階でも裏が取れなかったものは空欄のままにしてある。

### JANコードの調べ方

メーカー名と同じく、**単独の情報源では確定させない**。商品名の曖昧検索で拾うため、上位 10 件に目的の単品が 1 つも入らないことがある（「ココナッツクッキー」で 10 件すべて別商品だった実績がある）。

`fetch:yahoo` は候補（`_janCandidate`）を出すだけで、採否は `fetch:rakuten` が両者を突き合わせて決める。`_` で始まるキーは `build-data` が取り込まないため、Yahoo! 単独の判断が `lib/data.ts` に届くことはない。

| 状況 | 判定 | 件数 |
| --- | --- | --- |
| 両 API が一致 | 採用 | 41 |
| 片方だけが返した / 一致率 3 以上 | 採用 | 42 |
| 両 API が食い違った | **捨てる** | 37 |
| 片方だけが返した / 一致率 3 未満 | 捨てる | 29 |
| どちらも取れなかった | — | 17 |

食い違ったものを捨てるのは、中身が「まったくの別商品」ではなく**末尾が近い隣接 SKU**（味違い・入数違い）だから。商品名だけではどちらが井ノ口の売っている単品か機械的に決められない。

```
カンロ ザ・ストロンググミ ソーダ   yahoo=4901351026793 / rakuten=4901351026786
ポリッキー                       yahoo=4903013246556 / rakuten=4903013246563
```

一致率 3 をしきい値にしているのは、メーカー名の `MIN_BRAND_AGREEMENT` と同じ理由。実測で、両 API が一致した 36 件（当時）はいずれも Yahoo! 側で 2 件以上が同じ JAN を返しており、1 件しか一致しないものは 1 つも含まれていなかった。

### JANコードの正規化（`scripts/jan.mts`）

Yahoo! は JAN-8 を 13 桁にゼロ詰めして返すことがある。揃えないと同じ商品が「不一致」になって捨てられる。

```
うまい棒 めんたい味   Yahoo: 0000049480856   楽天: 49480856   ← 同じコード
```

ただし**先頭ゼロを無条件に剥がしてはいけない**。先頭の 0 が有意な 13 桁コードも実在する。

```
0096619816927  剥がすと 11 桁になり壊れる（009 は米国の事業者コード）
0000000000000  全ゼロのプレースホルダ。剥がすと空になる
```

見分けるのは**検査数字**（末尾 1 桁のモジュラス 10）。8 桁に戻して検査数字が通ればゼロ詰め、通らなければ 13 桁が正しい。人間が場合分けする必要がない。

正規形は 8 桁（JAN-8）と 13 桁（EAN-13）の 2 つで、12 桁の UPC-A は先頭に 0 を足して 13 桁に揃える。さらに先頭 2 桁が日本の事業者コード（`45` / `49`）でないものは、検索が別商品に流れた証拠として捨てる。

```
8938517587047 (893 ベトナム)   ← ココナッツクッキーの誤マッチ
9784098637393 (978 書籍のISBN) ← キャンディーボックスの誤マッチ
```

この検証は `build-data` でも再度かかるため、`overrides.json` に手で書いた JAN の打ち間違いもそこで止まる。

#### 国コードの制限は、正しい JAN も少し巻き込む

`45` / `49` 以外を捨てるルールは、**日本のメーカーが海外で製造した商品を巻き込む**。

```
ロングネックマシュマロ 12本入 (株)やおきん【原産国：フィリピン】
jan=4800029330777   ← 480 はフィリピンの GS1 コード
```

これは正しい JAN の可能性が高いが、捨てている。それでもこのルールを残しているのは、**得られる正確性の方が大きいため**。曖昧検索は日常的に別ジャンルへ流れるので、国コードはその大半を機械的に落とせる。

```
8938517587047 (893 ベトナム)   ココナッツクッキーの検索が海外商品に流れた
9784098637393 (978 ISBN)      キャンディーボックスの検索が書籍に流れた
```

**誤って弾く 1 件と、正しく弾く数件の交換**として受け入れている。海外製造の商品が増えてきたら、国コードではなく「ISBN(978/979) など明らかな非食品だけを弾く」形に見直す。

### カテゴリの決め方

商品名に含まれるキーワードで推定する（`scripts/fetch-inokuchi.mts` の `CATEGORY_RULES`）。当たらなかったものは「その他」に寄せる。

**キーワードには強さがある。** 以前は配列の並び順だけで決めていたため、せんべいのルールがスナックより前にあるというだけの理由で、うまい棒が味の名前に引きずられていた。

```
うまい棒 たこ焼味            → 「たこ」   → せんべい・おつまみ
うまい棒 スパイシービーフカレー味  → 「ビーフ」 → せんべい・おつまみ
```

| 強さ | 種類 | 例 |
| --- | --- | --- |
| 1 | 商品名・シリーズ名 | うまい棒、プリッツ、きのこの山 |
| 2 | 商品特性 | くじ、当たり、当て |
| 3 | 食品の種類 | ラムネ、グミ、せんべい、ポテト |
| 4 | 味・原材料 | ビーフ、たこ、梅、カツ |

単純な最長一致にはできない。並び順には意味のある優先度が混ざっているため。「ねり水あめ大当て」は `水あめ`（3 文字）の方が `当て`（2 文字）より長く、最長一致だと当たり付きだと分からなくなる。

**同じ強さの中では、終わりが右にあるものを採る。** 日本語の複合語は後ろが主役だから。

```
ドーナッツグミ    → 「ドーナ」ではなく「グミ」    （長さで決めると逆になる）
サワーコーラグミ  → 「コーラ」ではなく「グミ」
```

終わりが同じ位置なら長い方を採る。片方がもう片方を含む関係なので、長い方がより具体的に名指ししている（`甘いか太郎` > `太郎`）。

この結果、**配列の並び順は判定に影響しなくなった**。ルールを足すときに置き場所を悩まなくて済む。

### 同じシリーズは同じカテゴリになる

味違いをまたいでカテゴリが割れると、カテゴリで絞り込んだときにシリーズの一部だけが消える。シリーズ名を最も強いキーワードとして登録することで揃えている。

| シリーズ | 件数 | カテゴリ |
| --- | --- | --- |
| うまい棒 | 16 | スナック |
| 東豊ポテトフライ | 3 | スナック |
| すっぱい○○にご用心 | 3 | グミ・キャンディ |
| オリオン ミニ | 2 | ラムネ・タブレット |

「オリオン ミニ コーラ」はラムネ菓子であって飲料ではない。判定を変えた根拠は `CATEGORY_RULES` のコメントに残してある。

### ブランド名はカテゴリを決めない

「太郎」（菓道）と「さん太郎」は、**同じ名前で種類の違う商品が売られている**ため、キーワードとしてカテゴリを決める力を持たない。

| | 商品 |
| --- | --- |
| 珍味（魚肉すり身シート） | 蒲焼さん太郎 / 焼肉さん太郎 / のし梅さん太郎 / 酢だこさん太郎 / 甘いか太郎 / わさびのり太郎 |
| スナック（小麦菓子） | ラーメン屋さん太郎 / やきそば屋さん太郎 / 玉葱さん太郎 / キャベツ太郎 / 餅太郎 |

そのため「太郎」は弱いスナック判定として残しつつ、種類が違うものはフルネームで名指しして上書きしている。

### カテゴリの裏取り

推定結果は、`data/.cache/` に保存済みの**出品タイトル**で検算している。市場が付けた**ジャンル表示は使わない** — 出品者が付けた値なので、うまい棒が「ガム」、酢だこさん太郎が「ガム」になっている。

タイトルの説明語を数えるときも「おつまみ」は使わない。出品者はほぼ何にでも用途として書くため、プリッツも東豊ポテトフライも珍味に見えてしまう。「珍味」「スナック菓子」のように種類を名指しする語だけを数える。

キーワードで表せない個別の判断は `data/overrides.json` に `category` と `_categoryReason` で書く。

### 「飲料」カテゴリは廃止した

駄菓子屋に飲み物そのものはほぼ無い。該当していた 3 件を調べたところ、**1 件も飲料ではなかった**。

```
コーラスプラッシュ       やおきんの菓子。ジャンルは「飴、ソフトキャンディ」
フルーツパウダージュース   水に溶かす粉。「粉末ジュース」「パウダードリンク 粉末」
ポット入りフラワーヨーグル  ポット入りの練り菓子。検索ヒット 0 件
```

コーラ・サイダー・ヨーグルは、駄菓子では「味」か「菓子の名前」であって飲み物ではなかった。カテゴリごと削除し、7 カテゴリにしている。

## ガチャの確率設計

### 重み

```
weight = item.weight ?? (1 / price ^ GACHA_EXPONENT) / 同一シリーズの商品数
```

`GACHA_EXPONENT` は `lib/engine/gacha.ts` の定数で、現在は `2`。手応えの調整はこの数値ひとつで行う。

指数を 2 にしているのは価格差を増幅するため。10 円と 150 円の重み比は、指数 1 では 15 : 1 にしかならないが、指数 2 では 225 : 1 になる。

### シリーズによる重み補正

うまい棒のように味違いが多い商品をフラットに並べると、同じ重みの商品が大量に並び、そのシリーズだけで排出率を占有してしまう。実際、補正なしでうまい棒 20 種を入れるとシリーズ合計が 60% を超える。

そのため、シリーズに属する商品はシリーズ内の商品数で重みを割っている。これによりシリーズ全体の合計重みが単独商品 1 つぶんに揃い、**味を何種類増やしてもシリーズの出現率は変わらない**。

現在のデータでの排出率:

| 価格帯 | 排出率 |
| --- | --- |
| 10〜20 円 | 78.29% |
| 30〜50 円 | 20.45% |
| 60〜100 円 | 1.18% |
| 101 円〜 | 0.07% |
| （参考）うまい棒 16 種の合計 | 1.39% |

> **既知の問題**: 101 円超が 3 件しかなく、最高額帯の排出率が 0.07% まで下がっている。10 連を何度引いてもまず出ないため、「たまに出るとうれしい」体験が成立していない。商品数を増やすか `GACHA_EXPONENT` を下げるかの判断が必要。

## 予算モードのアルゴリズム

一様ランダムの貪欲法。重み付けは行わない。

```
1. カテゴリで候補を絞る
2. 残り予算で買えて、かつ両方の個数上限に達していない商品を抽出
3. その中から一様ランダムに 1 つ選び、残り予算を減らす
4. 抽出結果が空になったら終了
```

予算超過は、候補を抽出する段階で `価格 <= 残り予算` を満たす商品しか対象にしないため、構造的に発生しない。

重み付けをしていないにもかかわらず安価な商品が多く選ばれるのは、残り予算が減るにつれて高価な商品が候補から脱落していくため。安価な商品ほど候補に残る期間が長く、また 1 回あたりの予算消費が小さいぶん購入回数自体も多くなる。

## 設計方針

### エンジンは純粋関数にする

`lib/engine/` の関数は、駄菓子データも乱数も引数で受け取り、結果を返すだけ。React・DOM・データ取得のいずれにも依存しない。

- シードを固定できるため、確率の検証とテスト失敗の再現ができる
- テスト専用の小さなデータを渡せるため、理論値を手計算で検算できる
- `document` を触らないため Node.js 上で動き、10 万回規模のシミュレーションが数百ミリ秒で完了する

### データ取得は `repository.ts` に集約する

`lib/data.ts` を直接 import するのは `lib/repository.ts` のみ。それ以外は必ず `getAllDagashi()` を経由する。

この関数は中身が静的配列であるにもかかわらず `async` として定義してある。将来 DB へ移行した際、この関数の中身を差し替えるだけで済ませるため。

### 将来の拡張はフィールドとして先に用意する

`Dagashi` 型には、現時点では未使用のフィールドを含めてある。

| フィールド | 用途 |
| --- | --- |
| `rarity` | レア度システム。値が入ると価格ベースの判定より優先される |
| `weight` | ガチャ重みの手動上書き。**現時点で有効** |
| `imageUrl` | 商品画像。`null` の場合はカテゴリ絵文字を表示 |

取得元の 4 フィールド（`source` / `sourceId` / `sourceUrl` / `fetchedAt`）は**現時点で値が入っている**。`fetchedAt` は価格を取得した日時なので、価格を持たない情報源（Yahoo!・楽天）の取得日で上書きしない。手で価格を決めた商品は `source: "overrides"` になり、取得日時は持たない。

## テスト

```bash
npm test
```

すべて `lib/` 配下の純粋なロジックが対象で、ブラウザは起動しない。

| 対象 | 主な検証内容 |
| --- | --- |
| ガチャの確率 | 10 万回試行の実測排出率が理論値と一致すること。シードによる再現性 |
| シリーズ補正 | 味を 3 → 20 → 100 種に増やしてもシリーズ全体の出現率が変わらないこと。価格が混在していても成立すること |
| 予算超過 | 4 種類の予算 × 1000 回試行で一度も超過しないこと |
| 個数上限 | 商品上限・シリーズ上限が単独でも併用でも守られること |
| 境界値 | 予算 0 円 / 最安値未満 / 100 万円 |
| データ整合性 | ID の一意性、価格帯の分布、商品があるカテゴリは 3 件以上 |
| 取得元の情報 | JAN が 8/13 桁で検査数字を通ること、同じ JAN が 2 商品に付いていないこと、取得日時があること |

理論値との比較は、10 円と 100 円の 2 件のみのデータでも行っている。件数を絞ることで期待値（99% : 1%）を手計算で確認できるようにするため。
